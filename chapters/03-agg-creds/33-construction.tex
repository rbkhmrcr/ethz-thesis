\section{Construction}\label{sec:agg-creds-construction}

The protocol proceeds as follows. Each user first establishes a
pseudonymous identity with the registration authority. Issuers then issue
credentials to that identity for the attributes they certify. Before
presentation, the user aggregates the credentials corresponding to the
attributes they wish to disclose into a single aggregate signature. Finally, the
user proves knowledge of the aggregate credential and their registered identity
using a non-interactive zero-knowledge proof system.

The construction assumes that the registration authority ensures users' public
keys are unique, and that users hold the corresponding secret keys.
This prevents users from registering others' public keys and pooling credentials
across identities.  The registration authority assigns each user exactly one
tag, and signs only messages of the prescribed form: public keys and tags. A
malicious registration authority could violate these, for instance by assigning
duplicate tags or registering users under adversarially chosen identities.
Addressing this is orthogonal to our contribution.  We assume that verifiers
accept credentials only from the set of issuers with published public keys. This
prevents a malicious user from being able to impersonate an issuer to an honest
verifier.

\begin{outline}
  \item why each building block is the one it is
  \item RA signature: only has to stop a key and a tag it did not pair being passed off as paired; an ordinary EUF-CMA signature is enough, and nothing about its signatures needs hiding from it
  \item issuers: a presentation should show one short object, so signatures must aggregate; ordinary aggregate signatures would let two users pool theirs; multi-signatures restrict to one message, which is wrong since issuers sign different attributes; tag-based aggregation restricts to one tag, as required, without issuers coordinating
  \item proof system: zero knowledge so presentations reveal only the disclosed values; simulation extractable, not just sound, because the security proof simulates honest users' presentations while extracting from the adversary's, and soundness says nothing once the adversary has seen simulated proofs
  \item each presentation carries the verifier's message $\msg$ as its label, so it cannot be replayed elsewhere
\end{outline}

We now present the construction in full.

\paragraph{Setup.} During setup, the registration authority generates a key pair
for the digital signature scheme and public parameters for the proofs used
throughout the protocol. Each issuer independently generates a key pair for the
aggregate tag-based signature scheme. The registration authority's public key,
each issuer's public key, and the public parameters are published.

The registration authority (RA) samples a key pair $(\rask, \rapk) \sample
\DSgen(\secparam)$ and publishes~$\rapk$. Each of the $n$ issuers then samples
a key pair $(\isk{i}, \ipk{i}) \sample \ATSgen(\secparam)$ for the aggregate
tag-based signature scheme~$\ATS$ and publishes~$\ipk{i}$. The public parameters
$\crs$ consist of $\rapk$, the issuer public keys $\ipk{1}, \ldots, \ipk{n}$,
and the parameters of the proof system.

\paragraph{Registration.} During registration, the user establishes a long-term
pseudonymous identity with the registration authority. The user proves knowledge
of the secret key corresponding to their public key, after which the
registration authority binds that public key to a unique user tag. This tag is
what later links the credentials a user obtains from different issuers to one
another and to the user's registration: it is embedded in every credential
issued to the user, and at presentation the user proves that the same tag
underlies both their registration signature and their aggregated credentials,
without revealing which tag it is.

The user samples $\sk \sample \Zp$, sets $\pk = \gen^{\sk}$, and sends $\pk$ to
the RA together with a proof on a fresh $\msg$ from the RA that proves the user
knows the corresponding secret key $\sk$.  If the proof verifies, then the RA
assigns the user a unique tag~$\Tag$ and issues $\psi \sample \DSsign(\rask,
(\pk, \Tag))$.

The user initialises their credential state as $(\Tag, \sk, \pk, \psi, \cred_1,
\ldots, \cred_n)$, with $\cred_i = \varnothing$ for all $i \in [1,n]$, and
$\regcred = (\Tag, \pk, \psi)$ is their registration credential.

\paragraph{Issuance.} To obtain an attribute credential, the user authenticates
their registered identity to an issuer. If the issuer is satisfied that the user
possesses the requested attribute value, it issues an aggregate tag-based
signature on that attribute.

On input $(\Tag, \pk, \psi, \atv{i})$ from the user, the issuer checks that
$\psi$ verifies, and rejects if it does not.  Otherwise, the user next proves
knowledge of $\sk$.  If this succeeds and the user holds attribute value
$\atv{i}$, the issuer sends back $\signature_i \leftarrow \ATSsign(\isk{i},
\Tag, \atv{i})$. The user sets $\cred_i = (\atv{i}, \signature_i)$.

\paragraph{Aggregation.} Before presenting credentials, the user aggregates the
signatures corresponding to the attributes they wish to disclose into a single
aggregate signature. Aggregating under a common tag lets credentials issued by
different issuers be compressed into one short signature, so that presentation
requires a single proof of possession rather than one per issuer.

\paragraph{Presentation.} To prove possession of a collection of attributes, the
user aggregates the corresponding credentials and produces a proof.  This
simultaneously demonstrates possession of a valid registration credential and
that the aggregate signature verifies under the disclosed issuer public keys and
attribute values, without linking the presentation to the user's identity, to
their registration, or to any other presentation of the same underlying
credentials.

The user has $(\Tag, \sk, \pk, \psi, \cred_1, \ldots, \cred_n)$, where $\cred_i
= (\atv{i}, \signature_i)$.  To prove possession of attribute values
$(\atv{i})_{i \in \ISSUERS}$ to a verifier providing a fresh message $\msg$, the
user first constructs the aggregate signature as follows:
%
\begin{equation*}
%
  \signature \leftarrow \ATSaggregate((\signature_i)_{i \in \ISSUERS}),
 %
\end{equation*}
%
which, with the tag and the disclosed values, forms the aggregate credential
$\aggcred$. They then construct a proof of knowledge, with label $\msg$, with the
following parameters:
%
\begin{equation*}
%
  \inst_1 = (\rapk, \ISSUERS, \{\ipk{i}, \atv{i}\}_{i \in \ISSUERS}), \qquad
\witness_1 = (\Tag, \sk, \pk, \psi, \signature),
%
\end{equation*}
%
\begin{equation*} \begin{gathered}
%
  \rel_1 = \{\ \pk = \gen^{\sk} \ \wedge \
\DSverify(\rapk, (\pk, \Tag), \psi) = 1 \\
%
  \wedge\ \ATSverifyagg((\ipk{i})_{i \in \ISSUERS}, \Tag, (\atv{i})_{i \in
\ISSUERS}, \signature) = 1\ \}.
%
\end{gathered} \end{equation*}
%

\begin{outline}
  \item say $\rel_1$ in words: user knows $\sk$ of $\pk$, an RA signature $\psi$ on $(\pk, \Tag)$, and an aggregate signature under the same $\Tag$ on the disclosed values, one per issuer in $\ISSUERS$
  \item only the issuer set, issuer keys and disclosed values are public, so the presentation links neither to the user nor to other presentations
\end{outline}

\paragraph{Verification.} The verifier checks the proof with respect to the
disclosed attributes and issuer public keys. The presentation is accepted if and
only if the verification succeeds.

On input $(\{\atv{i}\}_{i \in \ISSUERS}, \msg, \algoproof)$, the verifier
returns the output of the proof verification algorithm.

\begin{theorem}\label{thm:agg-creds-construction-security} If $\DS$ is an
existentially unforgeable digital signature scheme, $\ATS$ an existentially
unforgeable aggregate tag-based signature scheme under tag-based aggregation,
and the proof system is zero knowledge and simulation extractable, then the above protocol securely realises ideal
functionality~$\idfu{\AAC}$.  \end{theorem}

\paragraph{Extensions.} The construction supports several straightforward
extensions.

\begin{outline}
  \item binding to a verifier and session: let $\msg$ contain the verifier's identity and a fresh nonce
  \item any subset of credentials can be presented by aggregating just that subset (aggregation is over $\ISSUERS$ only), with no further contact with issuers or the RA
\end{outline}

New issuers can join the system without impacting the construction. The
aggregation of credentials and their presentation is agnostic to the number of
issuers.

The construction as described assumes each issuer certifies a single attribute
type. To support an issuer certifying multiple attribute types under one key,
the issuer instead signs $(\Tag, \att{} \| \atv{})$ rather than $(\Tag,
\atv{})$, with $\att{}$ the attribute type and $\atv{}$ the attribute value.

The construction extends to epoch-based revocation. The registration authority
signs triple $(\pk, \Tag, \epoch)$ rather than pair $(\pk, \Tag)$, where
$\epoch$ identifies the current epoch, and issuers sign $(\Tag, \epoch \|
\atv{})$ rather than $(\Tag, \atv{})$, tying each attribute credential to that
epoch. At presentation, users additionally prove that their registration
signature and aggregate signatures all correspond to the current epoch.

We leave the study of accumulator-based revocation and the revocation of
individual attribute credentials to future work.
