\section{Definitions}\label{sec:offline-definitions}

\subsection{Offline payments}

An offline payment system involves five types of participants: the central bank,
intermediaries, users, a registration authority, and an auditor.

The central bank issues tokens to users and manages the reserves of the
intermediaries. Issuance is triggered by a withdrawal request from an
intermediary and, when successful, debits the issued value from that
intermediary's reserves. The central bank also redeems tokens on a deposit
request from an intermediary, crediting the redeemed value to the requesting
intermediary's reserves.

Users hold bank deposits at intermediaries, which they can exchange for tokens.
A user withdraws a token by submitting a withdrawal request to their
intermediary, which routes the request to the central bank. A successful
withdrawal debits the withdrawn value from the user's deposits and from the
intermediary's reserves. Once a user holds a token, they can use it in offline
payments. The token's lifecycle ends with a deposit, which lets its owner claim
bank deposits in exchange for the token. A deposit succeeds only if the token
was issued by the central bank, was initiated by its owner, and had not
previously been deposited.

Intermediaries maintain users' bank deposit accounts and mediate the interaction
of users with the central bank. They also onboard users into the system, opening
accounts for them and helping them obtain long-term credentials from the
registration authority.

The registration authority issues these long-term credentials, which users
subsequently use to authorise and authenticate payments.

The auditor is authorised to trace a fraudulent offline payment, such as one
that double spends a token, to its originator.

Each user's wallet consists of a mobile device and a secure element.

We assume the registration authority, the central bank, and the intermediaries
are honest but curious: they follow the protocol, but may collude with other
participants to learn information about offline payments.  The registration
authority is also trusted to assign each user a unique identifier, to
generate a correctly formed credential that will be accepted by all other
participants, and to issue that credential only following well-established KYC
processes.

Users may be arbitrarily malicious: they may collude to forge tokens, double
spend them, or steal the tokens of honest users, and may collude with other
participants to undermine the privacy of honest users. Users have full control
of their mobile devices, but we assume they cannot easily tamper with their
secure elements.

The auditor is fully trusted to inspect only fraudulent payments and to
deanonymise only misbehaving users.

We consider static corruption throughout: the adversary fixes the set of
corrupt participants before any protocol interaction takes place.

An offline payment scheme is defined by the following algorithms. We call the
scheme $\OP$, for offline payments, and prefix its algorithms with it. Account
creation is an operation of the intermediary rather than of the scheme, so we do
not give it as an algorithm here, though the ideal functionality below exposes
an interface for it. Throughout, we suppress the public parameters, the long-term credential, and the counterparty's inputs from the algorithm signatures,
and name only the state that distinguishes one call from another.

A token after $i$ payments is $T_i$, and each payment is one hop of the token's
chain. The secure element stores only a part $\tau_i$ of the token, the device
keeps its history $\algo{hist}_i$, and $d_n$ denotes the deposit request after
$n$ hops. The construction gives each of these in full.

\begin{description}

  \item[$(\pk_{\algo{cb}}, \ck, \pk_\auditor, \rapk) \sample
\OPgen(\secparam)$ :] The setup algorithm, on input security parameter
$\secparam$, generates the public keys of the central bank, the auditor, and the
registration authority, together with a public commitment key $\ck$.

  \item[$\cred \sample \OPregister(\rask)$ :] The registration algorithm, on
input the registration authority's secret key $\rask$, provisions the user's
secure element and outputs long-term credential $\cred$.

  \item[$T_0 \sample \OPwithdraw(v_0)$ :] The withdrawal algorithm, on input
value $v_0$, outputs token $T_0$ of that value, obtained by the user from the
central bank through their intermediary.

  \item[$p_i \sample \OPexecute(T_i)$ :] The payment algorithm, on input token
$T_i$, outputs payment $p_i$ transferring the token to the payee.

  \item[$\{0,1\} \sample \OPdeposit(\tau_n, \algo{hist}_n)$ :] The deposit
algorithm, on input the part $\tau_n$ of a token that the secure element stores
and the token's history $\algo{hist}_n$, returns 1 if
the token is redeemed for bank deposits and 0 otherwise.

  \item[$\algo{DS} \leftarrow \OPidentify(d_n, d_{n'})$ :] The identification
algorithm, on input two conflicting deposit requests $d_n$ and $d_{n'}$ for the
same original token, outputs the set $\algo{DS}$ of identifiers of the users who
double spent it.

\end{description}

\subsection{Building blocks}\label{sec:offline-building-blocks}

Besides the commitment, signature and encryption schemes of the preliminaries,
the construction needs two primitives that are not defined there, joint proofs
of knowledge and signatures on committed inputs.

\paragraph{Joint proofs of knowledge.}\label{sec:joint-pok-def} A joint proof
of knowledge (JPOK) lets two provers, each holding part of a witness, together
produce one proof of knowledge of the whole witness.

\paragraph{Syntax.} A JPOK $\JPOK$ is a proof system for a relation $\rel$ over
statement $\inst$ and witness $\witness = (\witness_0, \witness_1)$, where the first
prover holds $\witness_0$ and the second prover holds $\witness_1$. We
work in the random oracle model, so a JPOK has no setup algorithm and no common
reference string. A JPOK consists of the
following protocol and algorithm:

  \begin{description}

    \item[$\Phi \sample \JPOKprove_0(\inst, \witness_0) \leftrightarrow
\JPOKprove_1(\inst, \witness_1)$ :] The proving protocol, run between the
first prover on input statement $\inst$ and witness share $\witness_0$ and the
second prover on input statement $\inst$ and witness share $\witness_1$, gives
output proof $\Phi$ to the second prover.

    \item[$\{0,1\} \leftarrow \JPOKverify(\inst, \Phi)$ :] The
verification algorithm, on input statement $\inst$ and proof $\Phi$, outputs
$0$ or $1$.

  \end{description}

The verifier takes no part in the proving protocol, and receives only the proof.
We require completeness, zero knowledge and simulation extractability, defined
as follows.

\paragraph{Completeness.} A JPOK is complete if, for every statement $\inst$
and witness $(\witness_0, \witness_1)$ with $\rel(\inst, (\witness_0,
\witness_1)) = 1$ and every $\Phi \sample \JPOKprove_0(\inst, \witness_0)
\leftrightarrow \JPOKprove_1(\inst, \witness_1)$, the following holds:
%
\begin{equation*}
%
  \JPOKverify(\inst, \Phi) = 1.
%
\end{equation*}

\paragraph{Zero knowledge.} A JPOK is zero knowledge if it satisfies
\Cref{exp:zk}, where the oracle $\simoracle$, on input $(\inst, (\witness_0,
\witness_1))$ with $\rel(\inst, (\witness_0, \witness_1)) = 1$, runs the
proving protocol between two honest provers and returns $\Phi$ if $b = 0$, and
returns a simulated proof if $b = 1$.

\paragraph{Simulation extractability.} A JPOK is simulation extractable if it
satisfies \Cref{exp:simext} with verification algorithm $\JPOKverify$. The
adversary there produces the proof alone, so this covers a first and a second
prover that are both corrupt and collude.

\paragraph{Signatures on committed inputs.}\label{sec:sci-def} A signature
scheme on committed inputs (SCI) lets a recipient obtain a signature on a vector
of messages from a signer who sees only some of the messages and a commitment
to the others.

\paragraph{Syntax.} A signature scheme on committed inputs $\SCI$ consists of
the following algorithms. We index messages from $0$, and write $[n] = \{1,
\ldots, n\}$ and $[n]_0 = \{0, \ldots, n-1\}$ for a positive integer $n$.

\begin{description}

  \item[$(\sk, \pk) \sample \SCIgen(\secparam, \ell)$ :] The key generation
algorithm, on input security parameter $\secparam$ and vector length $\ell$,
outputs secret signing key $\sk$ and public verification key $\pk$ for messages
in $\Zp^\ell$.

  \item[$(\algo{req}, \state) \sample \SCIrequest(\pk, \msg, \algo{Disc})$ :]
The request algorithm, run by the recipient on input public key $\pk$, message
$\msg \in \Zp^\ell$ and set $\algo{Disc} \subseteq [\ell]_0$ of disclosed
indices, outputs request $\algo{req}$ and private state $\state$. The request
contains the disclosed messages $(\msg_i)_{i \in \algo{Disc}}$, a commitment $C$
to the other messages, and a proof $\algoproof_{\algo{req}}$ that $C$ is well
formed.

  \item[$\algo{resp} \sample \SCIissue(\sk, \algo{req})$ :] The issuing
algorithm, run by the signer on input secret key $\sk$ and request
$\algo{req}$, outputs response $\algo{resp}$ if $\algoproof_{\algo{req}}$
verifies and $\perp$ otherwise.

  \item[$\signature \leftarrow \SCIunblind(\state, \algo{resp})$ :] The
unblinding algorithm, run by the recipient on input private state $\state$ and
response $\algo{resp}$, outputs signature $\signature$ on $\msg$.

  \item[$\{0,1\} \leftarrow \SCIverify(\pk, \msg, \signature)$ :] The
verification algorithm, on input public key $\pk$, message $\msg$ and
signature $\signature$, outputs $0$ or $1$.

\end{description}

We write $\rel_{\algo{req}}$ for the relation that $\algoproof_{\algo{req}}$
proves. Its statement is $\pk$ together with the request without the proof, and
its witness is the hidden messages $(\msg_i)_{i \in [\ell]_0 \setminus
\algo{Disc}}$ together with the randomness of $C$.

\paragraph{Correctness.} An SCI scheme is correct if, for every key pair $(\sk,
\pk)$ generated by $\SCIgen(\secparam, \ell)$, every $\msg \in \Zp^\ell$, every
$\algo{Disc} \subseteq [\ell]_0$ and every $(\algo{req}, \state)$ generated by
$\SCIrequest(\pk, \msg, \algo{Disc})$, the following holds:
%
\begin{equation*}
%
  \SCIverify(\pk, \msg, \SCIunblind(\state, \SCIissue(\sk, \algo{req}))) = 1.
%
\end{equation*}

\paragraph{Existential unforgeability.} The signer sees only the disclosed
messages and a commitment to the others, so an experiment cannot tell which
messages it signed. In \Cref{exp:sci-euf} the adversary opens its accepted
requests at the end, and wins with a valid signature on a message that none of
them contains.

\begin{experimentbox}{Signatures on committed inputs: existential unforgeability}{sci-euf}

  \begin{enumerate}

    \item The challenger generates $(\sk, \pk) \sample \SCIgen(\secparam, \ell)$
and sends $\pk$ to $\adv$.

    \item The adversary is given oracle access to $\mathcal{O}_{\SCIissue}$,
which on input a request $\algo{req}$ returns $\algo{resp} \sample
\SCIissue(\sk, \algo{req})$ and, if $\algo{resp} \neq \perp$, adds $\algo{req}$
to the set $\mathcal{Q}$, which is initially empty.

    \item The adversary outputs $(\msg^\star, \signature^\star)$ and a witness
$\witness_{\algo{req}}$ for each $\algo{req} \in \mathcal{Q}$.

  \end{enumerate}

  For each $\algo{req} \in \mathcal{Q}$, let $\msg_{\algo{req}}$ be the message
with the disclosed messages of $\algo{req}$ and the hidden messages of
$\witness_{\algo{req}}$. $\adv$ wins the experiment if the following hold:
  %
  \begin{equation*}
  %
    \SCIverify(\pk, \msg^\star, \signature^\star) = 1 \ \wedge\ \forall
\algo{req} \in \mathcal{Q} : \rel_{\algo{req}}((\pk, \algo{req}),
\witness_{\algo{req}}) = 1 \ \wedge\ \msg^\star \neq \msg_{\algo{req}}.
  %
  \end{equation*}

\end{experimentbox}

The advantage of $\adv$ is defined as follows:
%
\begin{equation*}
%
  \Adv^{\mathsf{euf}}_{\SCI, \adv}(\secparam) = \Pr[\adv\text{ wins}].
%
\end{equation*}
%
We say the SCI scheme is existentially unforgeable if this advantage is
negligible for every PPT adversary $\adv$.

\paragraph{Request hiding.} Request hiding, defined by \Cref{exp:sci-hiding},
requires that a request reveal nothing beyond its disclosed messages, even to
the signer. It uses a simulator $\SCIsimrequest$ that, on input public
key $\pk$, disclosed messages $(\msg_i)_{i \in \algo{Disc}}$ and set
$\algo{Disc}$, outputs a request without access to the other messages. In the
random oracle model it may program the random oracle, as the proof simulator of
\Cref{sec:prelims-nizks} does. The definition is adapted from the blindness of
Coconut~\cite{NDSS:SABMD19}. The signer's key is generated honestly, which
suffices for an honest-but-curious signer.

\begin{experimentbox}{Signatures on committed inputs: request hiding}{sci-hiding}

  \begin{enumerate}

    \item The challenger samples $b \sample \{0,1\}$, generates $(\sk, \pk)
\sample \SCIgen(\secparam, \ell)$, and sends $(\sk, \pk)$ to $\adv$.

    \item The adversary is given oracle access to $\mathcal{O}_{\SCIrequest}$,
which on input $(\msg, \algo{Disc})$ with $\msg \in \Zp^\ell$ and $\algo{Disc}
\subseteq [\ell]_0$ returns $\algo{req}$, where $(\algo{req}, \state) \sample
\SCIrequest(\pk, \msg, \algo{Disc})$ if $b = 0$, and $\algo{req} \sample
\SCIsimrequest(\pk, (\msg_i)_{i \in \algo{Disc}}, \algo{Disc})$ if $b
= 1$.

    \item The adversary outputs a bit $b'$.

  \end{enumerate}

  $\adv$ wins the experiment if $b' = b$.

\end{experimentbox}

The advantage of $\adv$ is defined as follows:
%
\begin{equation*}
%
  \Adv^{\mathsf{hiding}}_{\SCI, \adv}(\secparam) = \left| \Pr[\adv\text{
wins}] - \frac{1}{2} \right|.
%
\end{equation*}
%
We say the SCI scheme is request hiding if this advantage is negligible for
every PPT adversary $\adv$.

\subsection{Security goals}

We define security of an offline payment scheme through an ideal
functionality. The properties it captures are stated
informally below and formalised in~\Cref{sec:ideal-func}.

An offline payment system must ensure the following:

\begin{description}

  \item[Unforgeability and theft prevention.] An honest payee, and the central
bank at deposit, accept a token only if the central bank issued it and the party
spending it owns it.

  \item[Double-spending identification and non-frameability.] An honest user
uses a token only once, in either a payment or a deposit. A token that is used
more than once is detected at deposit, and the auditor identifies the user who
double spent it. An honest user is never identified, even if every other user,
the intermediaries, and the central bank collude.

  \item[Conservation of value.] The total value in the system must not change
other than through issuance and redemption by the central bank. No sequence of
payments may create value, and the value credited on deposit must be the value
that was withdrawn.

  \item[User anonymity.] A payment reveals nothing about the honest users who
held the token before, beyond what is unavoidable: that the payee of the last
payment is the payer of the current one, and a growing list of random values
fixed throughout the token's lifetime. We assume the payer and the payee know
each other, and that this knowledge is not derived from the payment transcript.

  \item[Token unlinkability.] The intermediary of a user who withdraws or
deposits knows their identity, but the intermediaries and the central bank
cannot link a withdrawal of an honest user to a deposit except through the
value, even if they collude with every other user. A deposited token's history
reveals no more about earlier honest owners than a payment does.

\end{description}

\subsection{The ideal functionality for offline payments}\label{sec:ideal-func}

Secure realisation of the ideal functionality $\idfu{\algo{op}}$ by a protocol
is defined as in \Cref{sec:prelims-security}, in the standalone model.

$\idfu{\algo{op}}$ interacts with $\simu$ and with the participants at the start
of this section, under the trust assumptions given there. An individual holding
several bank accounts is modelled as several users, one per account. $\simu$
learns the inputs and outputs of the honest-but-curious participants, and
corrupts devices and secure elements only before they interact with
$\idfu{\algo{op}}$. \Cref{fig:ideal-func} gives the formal description, and we
summarise each interface below.

$\idfu{\algo{op}}$ works with the set $\algo{usrs}$ of users, the set $\algo{I}$
of intermediaries, and the sets $\algo{Dev}$ and $\algo{SE}$ of devices and
secure elements, where each user is a pair $\algo{usr} = (\algo{se},
\algo{dev})$. The registration authority is $\reg$, the central bank is
$\algo{cb}$ and the auditor is $\auditor$. The functionality keeps the set $\algo{mal}$ of
corrupt devices and secure elements, the set $\algo{registered}$ of registered
users, the map $\algo{accounts}$ from each user to their intermediary and
balance, and the map $\algo{reserves}$ from each intermediary to its reserves.
A token is a vector $\vec{\algo{id}}$ of random identifiers, one per hop, where
$\vec{\algo{id}}[0]$ is fixed at withdrawal. The map $\algo{tokens}$ sends a
token to its owner and value, and the map $\algo{deposited}$ sends
$\vec{\algo{id}}[0]$ to the vectors deposited for it. All maps start empty, and
unset entries are $\bot$. The longest common prefix of two identifier vectors
is the longest vector that both start with.

$\simu$ uses the corruption interface to compromise users' mobile devices or
secure elements. Corrupting a secure element also corrupts the device, since a
secure element is much harder to compromise. Intermediaries open accounts with
an initial value through the account creation interface, one per user. The
registration authority then registers a user who holds an account, once.

An intermediary calls the withdrawal interface for one of its users and a value.
If the user's account and the intermediary's reserves hold enough,
$\idfu{\algo{op}}$ gives the user a token with a fresh random identifier, which
$\simu$ chooses if the user's secure element is corrupt. $\simu$ learns the
identifier only if the user's device or secure element is corrupt, and otherwise
only the user and the value.

A registered user calls the execution interface to pay another registered user.
If the payee accepts, $\idfu{\algo{op}}$ checks that the token belongs to the
payer and has the claimed value, and records the payee as its owner under a
fresh identifier. A corrupt payee may accept an invalid token, but can never pass
it on to an honest user, since only valid tokens are recorded as owned. $\simu$
learns the payer and the payee only if one of their devices or secure elements
is corrupt, and otherwise only the value and the token's identifiers.

An intermediary calls the deposit interface for a registered user.
$\idfu{\algo{op}}$ checks that the token belongs to the user, has the claimed
value, and is the first deposit of its withdrawal, and then credits the user's
account and the intermediary's reserves with that value. $\simu$ learns the
deposit, since the central bank and the intermediary are honest but curious.

The auditor calls the identification interface with the first identifier of a
token. If the token was deposited more than once, $\idfu{\algo{op}}$ returns to
the auditor and the central bank the owner recorded at the longest common prefix
of each two deposited vectors.

Each informal goal above corresponds to
a specific behaviour of $\idfu{\algo{op}}$. Unforgeability is the check in
$\OPdeposit$ and $\OPexecute$ that $\algo{tokens}[\vec{\algo{id}}]$ is defined, so
that only tokens recorded at a prior $\OPwithdraw$ can be spent or redeemed.
Theft prevention is the stronger check that $\algo{tokens}[\vec{\algo{id}}]$ names
the calling user. Double-spending detection is the test on
$|\algo{deposited}[\vec{\algo{id}}[0]]|$ in $\OPdeposit$, and identification is
$\OPidentify$ returning the owner recorded at the longest common prefix. That this
owner is recorded rather than inferred gives non-frameability, since an
honest user is only ever written into $\algo{tokens}$ as the owner of a token
they were actually paid. Conservation of value is the pairing of the debits in
$\OPwithdraw$ with the credits in $\OPdeposit$, both of the same $v$, with no
interface that alters $\algo{accounts}$ or $\algo{reserves}$ otherwise.

Anonymity and unlinkability are what $\simu$ does not receive: on a withdrawal
by an honest user it learns the user and the value but not $\algo{id}$, and on the
matching deposit it learns $\vec{\algo{id}}$ but has no way to associate it with that
withdrawal.

    \begin{framed}

      \setlist[enumerate]{ topsep=2pt, partopsep=0pt, parsep=0pt, itemsep=1pt }

	Before any call to the offline payment interfaces, $\simu$ issues
corruption queries:

	\fuinterface{\OPcorrupt} Upon an active corruption request $(\OPcorrupt, P)$ for
$P \in \algo{Dev} \cup \algo{SE}$ from $\simu$ do: $\algo{mal} \gets \algo{mal}
\cup P$.

	\fuinterface{\OPcreate} Upon receiving for the first time $(\OPcreate,
\algo{usr}, v)$ from $\algo{Int} \in \algo{I}$ for $\algo{usr} \in \algo{usrs}$,
send $(\OPcreate, \algo{usr}, \algo{Int}, v)$ to $\simu$ and wait for the
go-ahead. On receiving it, do:

	\begin{enumerate}

	  \item If $\algo{accounts}[\algo{usr}] \neq \bot$, then stop.

	  \item Otherwise:

	    \begin{enumerate}

	      \item Set $\algo{accounts}[\algo{usr}] \leftarrow \langle
\algo{Int}, v\rangle$.

	      \item Set $\algo{reserves}[\algo{Int}] \leftarrow
\algo{reserves}[\algo{Int}]+v$.

	      \item Return $\OPcreateend$ to $\algo{Int}$.

	    \end{enumerate}

	\end{enumerate}

	\fuinterface{\OPregister} Upon receiving for the first time $(\OPregister,
\algo{usr})$ from $\reg$ for $\algo{usr} \in \algo{usrs}$ that already has an
account, send $(\OPregister, \algo{usr})$ to $\simu$ and wait for the go-ahead.
On receiving it, do:

	\begin{enumerate}

	  \item Set $\algo{registered} \gets \algo{registered} \cup \algo{usr}$.

	  \item Return $\OPregisterend$ to $\reg$.

	\end{enumerate}

	\fuinterface{\OPwithdraw} On receiving a $(\OPwithdraw, \algo{usr} = (\algo{se},
\algo{dev}), \algo{Int}, v)$ from registered user $\algo{usr}$ that has an
account with $\algo{Int}$, send $(\OPwithdraw, \algo{usr}, \algo{Int}, v)$ to
$\algo{Int}$ and $(\OPwithdraw, \algo{Int}, v)$ to $\algo{cb}$ and await their
go-ahead. Then send message $\OPwithdraw$ to $\simu$ and wait for the go-ahead.
On receiving it, fetch $\algo{accounts}[\algo{usr}] \rightarrow \langle
\algo{Int}, v^*\rangle$, and do:

	\begin{enumerate}

	  \item If $v^* < v$ or  $\algo{reserves}[\algo{Int}] < v$, then stop.

	  \item Otherwise, do:

	    \begin{enumerate}

	      \item Set $\algo{accounts}[\algo{usr}] \leftarrow \langle
\algo{Int}, v^* - v\rangle$.

	      \item Set $\algo{reserves}[\algo{Int}] \leftarrow
\algo{reserves}[\algo{Int}] - v$.

	      \item If $\algo{se} \not\in \algo{mal}$, then randomly select
$\algo{id}$.

	      \item Otherwise, receive $\algo{id}$ from $\simu$.

	      \item Write $\vec{\algo{id}} = (\algo{id})$. If $\algo{tokens}[\vec{\algo{id}}]
\neq \bot$, then stop.

	      \item Otherwise, do:

		\begin{enumerate}

		  \item Set $\algo{tokens}[\vec{\algo{id}}] \gets \langle \algo{usr},
v \rangle$.

		  \item If $\algo{se} \in \algo{mal}$ or $\algo{dev} \in
\algo{mal}$, then return $(\OPwithdraw, \algo{usr}, \algo{id}, v)$ to $\simu$.

		  \item Otherwise, return $(\OPwithdraw,\allowbreak \algo{usr},\allowbreak v)$ to
$\simu$.

		  \item Return $(\OPwithdraw, \algo{id}, v,$ $\OPwithdrawend)$
to $\algo{usr}$.

		\end{enumerate}

	    \end{enumerate}

	\end{enumerate}

	\fuinterface{\OPexecute} On receiving $(\OPexecute, \vec{\algo{id}}, v, \algo{usr}' =
(\algo{se}', \algo{dev}'))$ from registered user $\algo{usr} = (\algo{se},
\algo{dev})$ for registered user $\algo{usr}'$, send $(\OPexecute, \vec{\algo{id}},
v)$ to $\algo{usr}'$. On receiving the response $\algo{accept}$ from
$\algo{usr}'$, send $(\OPexecute, \vec{\algo{id}}, v)$ to $\simu$ and wait for the
go-ahead. On receiving it, do:

	\begin{enumerate}

	  \item If $\algo{se}' \not\in \algo{mal}$ and $\algo{dev}' \not\in
\algo{mal}$, then do:

	    \begin{enumerate}

	      \item If $\algo{tokens}[\vec{\algo{id}}] \neq \langle \algo{usr}, v
\rangle$, then stop.

	      \item Otherwise, do:

		\begin{enumerate}

		  \item Randomly select a unique random number $\algo{id}'$.

		  \item Set $\algo{tokens}[\vec{\algo{id}'}] \gets
\langle\algo{usr}', v \rangle$ where $\vec{\algo{id}'} = (\vec{\algo{id}}, \algo{id}')$.

		  \item If $\algo{se} \in \algo{mal}$ or $\algo{dev} \in
\algo{mal}$, then return $(\OPexecute, \vec{\algo{id}'}, v, \algo{usr}, \algo{usr}')$
to $\simu$.

		  \item Otherwise, return $(\OPexecute, \vec{\algo{id}'}, v)$ to
$\simu$.

		\end{enumerate}

	    \end{enumerate}

	  \item Otherwise, do:

	    \begin{enumerate}

	      \item If $\algo{se}' \in \algo{mal}$, then receive $\algo{id}'$ from
$\simu$.

	      \item Otherwise, randomly select $\algo{id}'$.

	      \item Set $\vec{\algo{id}'} = (\vec{\algo{id}}, \algo{id}')$.

	      \item If $\algo{tokens}[\vec{\algo{id}}] = \langle \algo{usr}, v
\rangle$, then set $\algo{tokens}[\vec{\algo{id}'}] \leftarrow \langle \algo{usr}', v
\rangle$.

	      \item Send $(\OPexecute,\vec{\algo{id}'}, v, \algo{usr}, \algo{usr}')$
to $\simu$.

	    \end{enumerate}

	  \item Return $(\OPexecute, \vec{\algo{id}'}, v, \OPexecuteend)$ to
$\algo{usr}'$, where $\vec{\algo{id}'}$ is as set above. If branch 1 stopped, return
nothing.

	\end{enumerate}

	\fuinterface{\OPdeposit} On receiving $(\OPdeposit, \vec{\algo{id}}, v, \algo{Int})$
from registered user $\algo{usr}$ that has an account with $\algo{Int}$, send
$(\OPdeposit, \vec{\algo{id}}, v, \algo{Int}, \algo{usr})$ to $\algo{Int}$ and
$(\OPdeposit, v, \algo{Int})$ to $\algo{cb}$ and await their go-ahead. Then send
$(\OPdeposit, \vec{\algo{id}}, v, \algo{Int}, \algo{usr})$ to $\simu$ and wait for
the go-ahead. On receiving it, do:

	\begin{enumerate}

	  \item If $\algo{tokens}[\vec{\algo{id}}] \neq \langle \algo{usr}, v
\rangle$, then stop.

	  \item Otherwise, do:

	    \begin{enumerate}

	      \item Set $\algo{deposited}[\vec{\algo{id}}[0]] \gets
\algo{deposited}[\vec{\algo{id}}[0]] \cup \{\vec{\algo{id}}\}$.

	      \item If $|\algo{deposited}[\vec{\algo{id}}[0]]| > 1$, then stop.

	      \item Otherwise, do:

		\begin{enumerate}

		  \item Fetch $\algo{accounts}[\algo{usr}] \rightarrow \langle
\algo{Int}, v^*\rangle$.

		  \item Set $\algo{accounts}[\algo{usr}] \gets \langle
\algo{Int}, v^*+v \rangle$.

		  \item Set $\algo{reserves}[\algo{Int}] \gets
\algo{reserves}[\algo{Int}] + v$.

		  \item Return $(\OPdeposit, \OPdepositend)$ to $\algo{usr}$.

		\end{enumerate}

	    \end{enumerate}

	\end{enumerate}

	\fuinterface{\OPidentify} On receiving $(\OPidentify, \algo{id})$ from $\auditor$,
send $(\OPidentify, \algo{id})$ to $\simu$ and wait for the go-ahead. On receiving
it, do:

	\begin{enumerate}

	  \item If $|\algo{deposited}[\algo{id}]| \leq 1$, then return $(\OPidentify,
\emptyset, \OPidentifyend)$ to $\auditor$.

	  \item Otherwise, do:

	    \begin{enumerate}

	      \item Fetch $\algo{deposited}[\algo{id}] \rightarrow \{\vec{\algo{id}}_1,
\cdots, \vec{\algo{id}}_n\}$.

	      \item Set $\algo{DS} \leftarrow \emptyset$.

	      \item $\forall i\neq j$, do:

		\begin{enumerate}

		  \item Let $\vec{\algo{id}}_{ij}$ be the longest common prefix
of $\vec{\algo{id}}_i$ and $\vec{\algo{id}}_j$.

		  \item Fetch $\algo{tokens}[\vec{\algo{id}}_{ij}] \rightarrow
\langle \algo{usr}_{ij}, v\rangle$.

		  \item Set $\algo{DS} \gets \algo{DS} \cup \algo{usr}_{ij}$.

		\end{enumerate}

	      \item Return $(\OPidentify, \algo{DS}, \OPidentifyend)$ to
$\auditor$ and $\algo{cb}$.

	    \end{enumerate}

	\end{enumerate}

    \end{framed}
