\section{Construction}\label{sec:offline-construction}

The construction $\OP$ works as follows. Each user enrols once with the
registration authority, which binds a secret key held in their secure element
to a unique identifier. Tokens are withdrawn through an intermediary and signed
by the central bank without it learning what it signs, and each payment extends
a chain of anonymous signatures that the token carries. The central bank
detects a token deposited twice, and the auditor then identifies the party
responsible and no one else.

The registration authority issues each user exactly one identifier, and issues
a credential only to a secure element that holds the corresponding secret key,
so users cannot accumulate identities. We assume identifiers are unpredictable
and not published by their owners. We do not assume that the secure element
succeeds in enforcing that a token is spent once.

\paragraph{Tokens.} A token is a value together with a pseudonym for its owner.
It is transferred whole, never split or merged, so a payment is a single
fixed-size operation. A token after $i$ payments is $T_i = (v, s_i, \com_i,
\algo{hist}_i)$. It consists of the value $v$, the randomness $s_i$, the
pseudonym $\com_i$ of its current owner, and the history $\algo{hist}_i$, which
is the transcript of the withdrawal and of the $i$ payments. The secure element
stores only $\tau_i = (v, \com_i)$.

The pseudonym is a commitment to the owner's identifier with randomness $s_i$.
Hiding makes a payment anonymous to anyone who reads its transcript, since a
user commits afresh for every token they hold. Binding ties the audit
ciphertext, which is proven consistent with the pseudonym, to one identifier.

\paragraph{Setup.} During setup the central bank generates a key pair for an
SCI scheme, the registration authority one for the credential signature scheme,
and the auditor an encryption key pair. The registration authority also signs
on committed inputs, since it must not learn users' secret keys. Its SCI scheme
needs only existential unforgeability and request hiding, and may be malleable,
since a credential is never shown, only proven. The auditor's encryption needs
only IND-CPA security, since every ciphertext it decrypts carries a proof that
it encrypts the identifier in a pseudonym, and an honest user's ciphertexts are
never decrypted.

\paragraph{Registration.} A user enrols once. Their secure element is
provisioned with a fresh secret key and a unique identifier, and the
registration authority issues a credential binding the two after the secure
element proves knowledge of the key, so the key never leaves the secure
element. The user's mobile device is then paired with the secure element, so
that the two communicate directly during payments.

\paragraph{Withdrawal.} The user's secure element generates a pseudonym for the
new token, and the device requests a signature on it through the intermediary,
which checks the user's funds. The central bank checks the intermediary's
reserves and signs on committed inputs. The request discloses the value, which
the central bank accounts for, and hides the identifier and the randomness, so
the central bank cannot later match the withdrawal to a deposit. Unforgeability
of the SCI scheme stops users minting tokens, and request hiding keeps the
central bank from learning whose token it signs. The value remains a channel,
so a deployment should use a small set of fixed denominations.

The signature is never shown, since verifying it requires the withdrawer's
identifier. The device instead proves knowledge of it once, at withdrawal, and
every later payee verifies this proof of withdrawal. This is why the central
bank signs on committed inputs rather than with a blind signature scheme, as
there is no later showing for blindness to protect. Nothing binds the committed
identifier to the withdrawing user, and nothing needs to. Spending requires a
credential on that identifier, so a user who commits to somebody else's
identifier only destroys their own funds.

\paragraph{Payment.} The payee's secure element generates a fresh pseudonym and
sends it to the payer. The payer's secure element locks the token, the payer's
device encrypts the payer's identifier under the auditor's key, and the two
jointly produce a signature of knowledge over the value and both pseudonyms.
The payer sends the payee the token, the ciphertext, the signature and the
token's history, and the payer's secure element deletes the token on
acknowledgement.

Signing the payee's pseudonym fixes the destination, so nobody who sees the
signature can redirect the token. The payee chooses that pseudonym so that two
payments of the same token to the same payee still differ, and the point at
which two histories diverge names the payer. A payee who deliberately reuses
its randomness only moves the divergence one link along, and is identified
itself.

The ciphertext is there because an offline payee cannot ask anyone who the
payer is, so what the auditor needs must be sealed in the transcript. The device
proves that the ciphertext matches the pseudonym it spends under. This stops a
double spender sealing someone else's identity, and stops a malicious payer
choosing the pseudonym for an honest payee, which would need the payee's
identifier. The audit proof and the transfer signature prove knowledge of the
same opening, but are kept separate, because the device produces the audit
proof alone.

The transfer signature is a JPOK, since the secret key must never leave the
secure element and generic two-party computation is too much for it. The secure
element contributes only knowledge of the key, and the device supplies the rest
of the witness and of the proof, so the scheme runs on existing hardware. The
payee verifies every link before accepting, so the transcript and its
verification grow by one link per transfer. \Cref{sec:offline-evaluation}
measures both.

A payment that stops part way loses no value. Once the payer's secure element
has signed, it is locked to that destination. Whether the payment or the
acknowledgement was lost, a retry completes the payment, and the token cannot be
spent elsewhere. A secure element that resets to escape the rule destroys the
token it held.

\paragraph{Deposit.} The final owner signs the token over to the central bank
through their intermediary, with their own audit ciphertext and proof as in a
payment, but over a fixed deposit marker in place of a payee pseudonym. The
marker stops a deposit being replayed as a payment, and the ciphertext lets the
auditor name a user who deposits a token and also pays it onward or deposits it
again. The central bank verifies the chain and credits the account unless it
has seen a deposit with the same original pseudonym. This is the only part of a
token that transfers do not change, so a conflict cannot be hidden by paying
the token along a different route. A second deposit is refused and credits
nothing, so the total value is unchanged, unlike in schemes where the issuer
absorbs the double-spent value~\cite{Beer2024}. The central bank keeps the
conflicting requests for the auditor. Compensating an honest holder who was
paid an already-spent token, and any consequences for the named user, are
outside the scheme.

\paragraph{Identification.} Two conflicting deposits of one token agree on a
prefix and then differ, because the owner at that point either sent two
payments or deposited the token and also paid it onward. The auditor decrypts
the ciphertext at the last position where the two agree and recovers that
owner's identifier. Earlier ciphertexts belong to owners who passed the token
on once, and are never opened.

This is anonymity revocation for a known double spend, not the general-purpose
auditing of \Cref{chap:txid}. Ecash schemes without an auditor let anyone
compute a double spender's identity from two payments of the same token,
through cut and choose, linear equations in the user's secret, or
double-spending tags. Some also cover transferable tokens, at a higher cost per
payment~\cite{C:ChaFiaNao88,C:Brands93,EC:CamHohLys05,PKC:BCFK15}.

\Cref{prot:offline} gives the complete protocol. It is stated generically with
respect to the underlying commitment scheme, digital signature scheme, SCI
scheme, public-key encryption scheme, and JPOK, and the next section
instantiates each of them.

\begin{protocolbox}{Offline payments}{offline}

  \begin{description}

    \item[$(\pk_{\algo{cb}}, \ck, \pk_\auditor, \rapk) \sample
      \OPgen(\secparam)$ :] On input security parameter $\secparam$, do:

      \begin{enumerate}

        \item The central bank generates keys for an SCI scheme on vectors of
          three messages, $(\sk_{\algo{cb}}, \pk_{\algo{cb}}) \sample
          \SCIgen(\secparam, 3)$.

        \item Run $\ck \sample \ComGen(\secparam)$ to obtain a public
          commitment key.

        \item The auditor generates an asymmetric encryption key pair
          $(\sk_\auditor, \pk_\auditor) \sample \PKEgen(\secparam)$.

        \item The registration authority generates keys for an SCI scheme on
          vectors of two messages, $(\rask, \rapk) \sample \SCIgen(\secparam,
          2)$.

        \item Publish all public keys and generators to every participant, and
          return $(\pk_{\algo{cb}}, \ck, \pk_\auditor, \rapk)$.

      \end{enumerate}

    \item[$\cred \sample \OPregister(\rask)$ :] When a user opens an account,
      do the following:

      \begin{enumerate}

        \item Provision the user's secure element $\algo{se}$ with a fresh
          secret key $\sk_{\algo{usr}}$ and a unique random identifier
          $\algo{uid}$.

        \item $\algo{se}$ runs $(\algo{req}, \state) \sample \SCIrequest(\rapk,
          (\algo{uid}, \sk_{\algo{usr}}), \{0\})$, which discloses $\algo{uid}$
          and commits to $\sk_{\algo{usr}}$, and sends $\algo{req}$ to the
          registration authority. Its proof is bound to a fresh nonce from the
          registration authority, so that nobody can replay it.

        \item The registration authority verifies that $\algo{uid}$ is fresh
          and returns $\algo{resp} \sample \SCIissue(\rask, \algo{req})$, and
          $\algo{se}$ computes $\varphi \leftarrow \SCIunblind(\state,
          \algo{resp})$. The registration authority does not learn
          $\sk_{\algo{usr}}$.

        \item $\algo{se}$ stores credential $\cred = (\algo{uid}, \varphi)$,
          which satisfies the following:
          %
          \begin{equation*}
          %
            \SCIverify(\rapk, (\algo{uid}, \sk_{\algo{usr}}), \varphi) = 1.
          %
          \end{equation*}

        \item Pair the user's mobile device $\algo{dev}$ with $\algo{se}$, so
          that only $\algo{dev}$ can send instructions to $\algo{se}$. At
          pairing, $\algo{se}$ hands $\algo{dev}$ the credential $(\algo{uid},
          \varphi)$, which $\algo{dev}$ needs for its part of the JPOK. It does
          not hand over $\sk_{\algo{usr}}$.

        \item Return $\cred$.

      \end{enumerate}

    \item[$T_0 \sample \OPwithdraw(v_0)$ :] The user withdraws a token of value
      $v_0$. Do the following:

      \begin{enumerate}

        \item The user's mobile device instructs their secure element to
          initiate a withdrawal of value $v_0$.

        \item The secure element selects a random $s_0$, computes the pseudonym
          $\com_0 \leftarrow \ComCommit(\ck, \algo{uid}_0, s_0)$, and returns
          $(s_0, \com_0)$ to the device.

        \item The device requests a signature on $(\algo{uid}_0, v_0, s_0)$
          that discloses $v_0$ alone, the message at index $1$, $(\algo{req},
          \state) \sample \SCIrequest(\pk_{\algo{cb}}, (\algo{uid}_0, v_0,
          s_0), \{1\})$, and sends $\algo{req}$ to the intermediary. The
          commitment $C$ in $\algo{req}$ commits to the hidden messages under
          $\pk_{\algo{cb}}$, and is a different object from the pseudonym
          $\com_0$, which commits to $\algo{uid}_0$ alone under $\ck$.

        \item The intermediary locks $v_0$ in the user's account and forwards
          $\algo{req}$ to the central bank.

        \item The central bank checks that $C$ is fresh, computes $\algo{resp}
          \sample \SCIissue(\sk_{\algo{cb}}, \algo{req})$, aborts if it is
          $\perp$, and otherwise debits the intermediary's reserves and returns
          $\algo{resp}$.

        \item The device computes $\psi \leftarrow \SCIunblind(\state,
          \algo{resp})$, with $\SCIverify(\pk_{\algo{cb}}, (\algo{uid}_0, v_0,
          s_0), \psi) = 1$, and stores $(v_0, s_0, \com_0, \psi)$. The secure
          element stores the original token $\tau_0 = (v_0, \com_0)$.

        \item The device produces a proof of withdrawal $\Sigma$ with $\inst =
          (\ck, \pk_{\algo{cb}}, v_0, \com_0)$, $\witness = (\algo{uid}_0, s_0,
          \psi)$, and relation as follows:
          %
          \begin{equation*}
          %
            \SCIverify(\pk_{\algo{cb}}, (\algo{uid}_0, v_0, s_0), \psi) = 1
            \;\wedge\; \com_0 = \ComCommit(\ck, \algo{uid}_0, s_0).
          %
          \end{equation*}

        \item Return $T_0 = (v_0, s_0, \com_0, \algo{hist}_0 = \Sigma)$.

      \end{enumerate}

    \item[$p_i \sample \OPexecute(T_i)$ :] The payer pays the payee using token
      $T_i = (v, s_i, \com_i, \algo{hist}_i)$. Do the following:

      \begin{enumerate}

        \item The payee's device instructs their secure element to prepare to
          receive a payment of value $v$.

        \item The payee's secure element selects a random $s_{i+1}$, computes
          $\com_{i+1} \leftarrow \ComCommit(\ck, \algo{uid}_{i+1}, s_{i+1})$,
          and returns $(s_{i+1}, \com_{i+1})$ to their device.

        \item The payee's device sends $\com_{i+1}$ to the payer's device.

        \item The payer's device notifies their secure element that a payment
          is under way. The secure element locks token $\tau_i = (v, \com_i)$.

        \item The payer's device computes the audit ciphertext $\ciph_i
          \leftarrow \PKEencrypt(\pk_\auditor, \algo{uid}_i; \rho_i)$ and a
          proof of correctness $\Gamma_i$, with $\inst = (\ck, \pk_\auditor,
          \com_i, \ciph_i)$, $\witness = (\algo{uid}_i, s_i, \rho_i)$, and
          relation as follows:
          %
          \begin{equation*}
          %
            \com_i = \ComCommit(\ck, \algo{uid}_i, s_i) \;\wedge\; \ciph_i =
            \PKEencrypt(\pk_\auditor, \algo{uid}_i; \rho_i).
          %
          \end{equation*}

        \item The payer's secure element and device jointly compute $\sigma_i$,
          a signature of knowledge on the message $m_i = (v, \com_i,
          \com_{i+1})$ for the relation as follows:
          %
          \begin{equation*}
          %
            \SCIverify(\rapk, (\algo{uid}_i, \sk_{\algo{usr}_i}), \varphi_i) =
            1 \;\wedge\; \com_i = \ComCommit(\ck, \algo{uid}_i, s_i).
          %
          \end{equation*}
          %
          This is a JPOK, in which the secure element runs $\JPOKprove_0$ and
          contributes knowledge of the payer's secret key, and the device runs
          $\JPOKprove_1$ and contributes the remaining witness.

        \item The payer's device sends payment $p_i = (v, \com_i, \com_{i+1},
          \ciph_i, \sigma_i, \Gamma_i, \algo{hist}_i)$ to the payee's device.

        \item The payee's device verifies $\algo{hist}_i$: if $i = 0$, it
          checks $\Sigma$. Otherwise it verifies $\Sigma$ and every $(\Gamma_k,
          \sigma_k)_{k \in [0, i-1]}$.

        \item If $\Gamma_i$ and $\sigma_i$ also verify, the payee's device
          accepts and stores $T_{i+1} = (v, s_{i+1}, \com_{i+1},
          \algo{hist}_{i+1} = (\com_i, \ciph_i, \sigma_i, \Gamma_i) \, \| \,
          \algo{hist}_i)$, and their secure element stores $\tau_{i+1} = (v,
          \com_{i+1})$.

        \item Upon acknowledgement, the payer's secure element deletes
          $\com_i$, and their device returns $p_i$.

      \end{enumerate}

    \item[$\{0,1\} \sample \OPdeposit(\tau_n, \algo{hist}_n)$ :] The user
      deposits token $\tau_n = (v, \com_n)$. Do the following:

      \begin{enumerate}

        \item The user instructs their device to deposit $\tau_n$. The device
          instructs the secure element to lock $\tau_n$.

        \item The device computes the audit ciphertext $\ciph_n \leftarrow
          \PKEencrypt(\pk_\auditor, \algo{uid}_n; \rho_n)$ and proof
          $\Gamma_n$, exactly as in $\OPexecute$.

        \item The device and secure element jointly compute $\sigma_n$, a
          signature of knowledge on the message $m_n = (v, \com_n, \algo{dep})$
          for the relation of $\OPexecute$, where $\algo{dep}$ is a fixed
          marker distinct from every pseudonym.

        \item The device sends deposit request $d_n = (\tau_n, \ciph_n,
          \sigma_n, \Gamma_n, \algo{hist}_n)$ to the intermediary, which
          forwards it to the central bank.

        \item The central bank verifies $\sigma_n$, $\Gamma_n$, and
          $\algo{hist}_n$.  If any check fails, return $0$.

        \item Otherwise, the central bank checks whether any prior deposit
          shares the same origin $\com_0$. If so, it records double spending,
          notifies the auditor, and returns $0$.

        \item Otherwise, the central bank credits the intermediary's account,
          which in turn credits the user's account, and the secure element
          deletes $\tau_n$ upon notification.

        \item Return $1$.

      \end{enumerate}

    \item[$\algo{DS} \leftarrow \OPidentify(d_n, d_{n'})$ :] On input two
      conflicting deposit requests $d_n$ and $d_{n'}$ involving the same
      original token, the auditor does:

      \begin{enumerate}

        \item Parse $d_n$ into the pseudonyms $(\com_k)_{k \in [0, n]}$ and
          ciphertexts $(\ciph_k)_{k \in [0, n]}$ it contains, taking these from
          $\algo{hist}_n$ together with the depositor's own $\com_n$ and
          $\ciph_n$, and parse $d_{n'}$ analogously into $(\com'_k)_{k \in [0,
          n']}$ and $(\ciph'_k)_{k \in [0, n']}$.

        \item Find the largest index $j$ such that $\com_k = \com'_k$ for all
          $k \leq j$. Either $\com_{j+1} \neq \com'_{j+1}$, in which case the
          owner at $j$ sent two different payments, or one of the two chains
          ends at $j$, in which case the owner at $j$ deposited the token and
          also spent or deposited it a second time. Both requests carry
          $\ciph_j$.

        \item Decrypt $\ciph_j$ using $\sk_\auditor$ to recover $\algo{uid}^*$,
          the identifier of the owner of $\tau_j = (v, \com_j)$.

        \item Return $\algo{DS} = \{\algo{uid}^*\}$, extended by repeating the
          above for each further pair of conflicting deposits of the same
          token.

      \end{enumerate}

  \end{description}

\end{protocolbox}

\begin{theorem}\label{thm:offline-construction-security}
  %
  If the commitment scheme is hiding and binding, the public-key encryption
  scheme is IND-CPA secure, the central bank's SCI scheme is existentially
  unforgeable and request hiding, the registration authority's SCI scheme is
  existentially unforgeable and request hiding, and the proofs and signatures
  of knowledge, including the JPOK and the request proof, are zero knowledge
  and simulation extractable, then $\OP$ securely realises ideal functionality
  $\idfu{\algo{op}}$ against static corruption of users, with the registration
  authority, the central bank, and the intermediaries honest but curious.
%
\end{theorem}

\paragraph{Extensions.} The construction supports several extensions, each a
change to the construction rather than to its instantiation.

\paragraph{Epochs.} An epoch is a fixed period after which credentials and tokens are no longer
accepted. The construction extends to expiry by epochs, which is how it
accommodates revocation. The registration authority signs the triple
$(\algo{uid}, \sk_{\algo{usr}},\allowbreak \epoch)$ rather than the pair
$(\algo{uid}, \sk_{\algo{usr}})$, and the central bank signs
$(\algo{uid}_0,\allowbreak v,\allowbreak s_0,\allowbreak \epoch)$ at
withdrawal, tying each token to the epoch in which it was issued. Both schemes
sign vectors one message longer, and the proof of withdrawal and the JPOK each
prove one more message. Nothing else changes.

Payees enforce the policy, rejecting payments carrying an epoch outside the
window they accept, and the width of that window can be tuned to the value of
the payment. An epoch can equally be counted in spending hops rather than in
wall-clock time, capping the length of a chain that will be accepted at
deposit.

A payee who has been offline since before a payer was revoked has no verified
real-time information with which to reject that payer, so the guarantee is
expressed as a bound on how long a credential remains usable rather than as an
instruction delivered to payees.

Epochs are disclosed, so they narrow the anonymity set of a withdrawal to the
users who withdrew the same denomination in the same epoch, and a deployment
should choose the epoch width with that in mind.

\paragraph{Payment caps.} Capping the value of an individual payment extends the construction in the same
direction and composes with epochs. Together the two bound the value a
compromised wallet can move before its tokens expire, making double spending
financially unattractive independently of whether the spender is subsequently
identified. Both are payee-side checks and require no change to the protocol
messages.

\paragraph{Secure element hardware.} The secure element can be any hardware that protects the key and the single-use
logic together. Smart cards do. Mobile trusted execution environments are
isolated parts of a phone's main processor, and they protect keys but not the
logic that uses them~\cite{trustzone,secureenclave,javacard,mifare}.

\paragraph{Recovery.} The requirement that $\sk_{\algo{usr}}$ never leave the secure element extends
to a recovery mechanism at the credential layer. A user who loses their device
re-enrols with the registration authority under a fresh pair $(\algo{uid},
\sk_{\algo{usr}})$, restoring their ability to transact without migrating any
state. The unspent tokens held by the lost device are not recoverable, since no
other party holds the commitment randomness needed to spend them. This matches
the behaviour of cash, and of the deployed offline systems discussed in the
introduction.

\paragraph{Pruning.} The central bank needs its list of deposited tokens to detect double spending,
so it cannot simply discard it. Logical or wall-clock timestamps that bound a
token's validity span let it prune entries once that span has elapsed.

\paragraph{Coin transparency.} Like physical cash, $\OP$ does not provide coin
transparency.
