\section{Definitions}\label{sec:txid-definitions}

A tracing protocol involves four types of participants. The ledger operator
maintains a publicly accessible, append-only ledger that stores submitted
transactions, and runs the transaction validators that decide, on input of the
ledger, which transactions are valid. We assume the ledger operator is honest,
so that the ledger itself is available and correctly maintained. The
registration authority authenticates users and issues the credentials required
to submit transactions and enable selective traceability. It is honest but
curious during the protocol, so it follows the protocol but tries to learn what
it can from what it sees. We also assume it does not bias the public
parameters. Users are potentially malicious, and generate and submit
confidential transactions. They decide which auditors are authorised to trace
them, and during which epochs. Auditors are
potentially malicious, and may be granted permission to trace the transactions
of specific users during specific epochs. Time is divided into epochs, numbered
consecutively, and the ledger operator advances the current epoch on a schedule
fixed in the public parameters.

We consider static corruption throughout: the simulator corrupts users and
auditors of its choice before any call to the ideal functionality is made.

A tag-based tracing protocol $\ID$ consists of the following algorithms.

\begin{description}

  \item[$(\crs,\state) \sample \IDgen(\secparam)$ :] The setup algorithm, on
input security parameter $\secparam$, generates the public ledger parameters
$\crs$ together with the initial ledger state $\state$.

  \item[$(\sk,\utk,\regcred) \sample \IDregister(\crs,\state)$ :] The
registration algorithm, run interactively between a user and the registration
authority on input public parameters $\crs$ and state $\state$, outputs user
signing key $\sk$, tracing key $\utk$, and registration credential $\regcred$ to
the user.

  \item[$(\PTK,\ek) \sample \IDgrant(\crs,\sk,\utk,\regcred,\epoch)$ :] The
authorisation algorithm, run interactively between a user and an auditor on
input public parameters $\crs$, signing key $\sk$, tracing key $\utk$,
registration credential $\regcred$, and epoch $\epoch$, outputs the user's
certified public tracing key
$\PTK$ and the epoch tracing key $\ek$ to the auditor.

  \item[$\tx \sample \IDsubmit(\crs,\sk,\utk,\regcred,\epoch,\payload)$ :] The
submission algorithm, on input public parameters $\crs$, signing key $\sk$,
tracing key $\utk$, registration credential $\regcred$, epoch $\epoch$, and
transaction payload $\payload$, outputs transaction $\tx$, which the user sends
to the ledger
operator.

  \item[$\{0,1\} \leftarrow \algo{Verify}(\crs,\state,\tx)$ :] The validation
algorithm, run by the transaction validators on input public parameters $\crs$,
current ledger state $\state$, and transaction $\tx$, returns $1$ if $\tx$ is to
be appended to the ledger and $0$ otherwise. It is non-interactive, so a validator
contacts neither the sender, nor the registration authority, nor any auditor.

  \item[$\{\payload\} \leftarrow \IDidentify(\crs,\PTK,\ek,\epoch)$ :] The
tracing algorithm, on input public parameters $\crs$, public tracing key $\PTK$,
epoch tracing key $\ek$, and epoch $\epoch$, returns the set of payloads of the
transactions submitted under $\ek$ during $\epoch$.

\end{description}

\subsection{The ideal functionality for tracing}

We define security of tracing through an ideal functionality
$\idfu{\algo{trace}}$ that represents a trusted third party which executes the
operations of the ledger on behalf of system participants, and which by
construction satisfies the three properties set out below.

Anonymity means
that only an auditor holding a tracing permission for a user and epoch can
de-anonymise that user's transactions during that epoch. Non-repudiation means
that every transaction a user submitted during an epoch can be traced back to
them by any auditor holding a permission for that user and epoch. Permission
expiration means that a permission covers only the epoch for which it was
granted. Once that epoch ends, the auditor cannot trace the user's later
transactions, or those of earlier epochs, but can still trace those of the
granted epoch.

The functionality does not capture two things. First, it models unlinkability
of a transaction to its originator and not confidentiality of the transaction
payload. The ledger is public, so $\idfu{\algo{trace}}$ hands every submitted
payload to the simulator $\simu$ on every $\IDsubmit$ call and withholds only
the identity of the submitting user.
The underlying transaction system provides confidentiality of the payload, and
this is orthogonal to what we prove here. Second, it does not capture
retrospective disclosure, and this is a limitation of our model. $\IDgrant$
accepts only epochs that have not started, so users grant a permission before
the epoch it covers, and an auditor cannot be given access to an epoch that has
already started. A user cannot refuse to
be traced in an epoch for which they have already granted a
permission.

Secure realisation of $\idfu{\algo{trace}}$ by a protocol is defined as in
\Cref{sec:prelims-security}, in the standalone model.


The formal description is given in~\Cref{fig:ftxid}, and we summarise it here.

The functionality keeps three tables: $\reg$ records which users are
registered, $\txns$ the payloads each user submitted in each epoch, and $\perm$
the tracing permissions users granted to auditors. It also keeps the current
epoch $\epoch_{\mathsf{cur}}$, which starts at $1$, and $\Cor$ is the set of
participants $\simu$ corrupted before the first call.

Users call $\IDregister$ to join the system.
Registration succeeds if the registration authority approves, and each user can
register only once. Registered users then call $\IDsubmit$ to submit up to a
fixed number $\Max$ of transactions per epoch, each for the current epoch. Each
successful call records the payload together with the identity of the user and
the epoch. $\simu$ also learns who submitted a payload when that user is corrupt. The functionality subsumes
$\algo{Verify}$, as a call that passes its checks corresponds to a transaction that
the validators accept.

To make their transactions traceable, users call $\IDgrant$ to authorise an auditor to trace
their transactions for a specific epoch. $\idfu{\algo{trace}}$ records that the
auditor is authorised to trace the user's transactions for that epoch, provided the epoch has not started. A grant covers that one epoch
only, and tracing another epoch needs another grant.
Auditors call $\IDidentify$ to obtain the payloads of
the transactions a user submitted in an epoch, and succeed only with a
permission for that user and epoch. They then receive every such transaction,
which gives non-repudiation. $\simu$ also learns the traced payloads when the
auditor is corrupt. Finally, the ledger operator calls $\IDincepoch$ to move all
participants to the next epoch, on the schedule described above.

    \begin{framed}

      \setlist[enumerate]{ topsep=2pt, partopsep=0pt, parsep=0pt, itemsep=1pt }

      $\idfu{\algo{trace}}$ keeps tables $\reg$, $\txns$ and $\perm$, the set
$\Cor$ of corrupt participants, and the epoch $\epoch_{\mathsf{cur}} = 1$.

	\fuinterface{\IDregister} On input register from the user $\user$, send
$(\IDregister, \user)$ to the registration authority and wait for confirmation.
On receiving confirmation, do the following:

	\begin{enumerate}

	  \item If $\reg[\user] \neq \bot$, then stop.

	  \item Send $(\IDregister, \user)$ to $\simu$ and wait for the
go-ahead. On receiving it, continue.

	  \item Set $\reg[\user] \leftarrow \mathsf{true}$.

	  \item Return $\IDregisterend$ to $\user$ and $\simu$.

	\end{enumerate}

	\fuinterface{\IDsubmit} On input $(\IDsubmit, \payload, \epoch)$ from $\user$,
do:

	\begin{enumerate}

	  \item If $\reg[\user] = \bot$, then stop.

	  \item If $\epoch \neq \epoch_{\mathsf{cur}}$, then stop.

	  \item If $|\txns[(\user,\epoch_{\mathsf{cur}})]| + 1 > \Max$, then
stop.

	  \item If $\user \in \Cor$, then $\mathsf{origin} \leftarrow \user$, and
otherwise $\mathsf{origin} \leftarrow \varnothing$.

	  \item Send $(\IDsubmit, \payload, \epoch, \mathsf{origin})$ to
$\simu$, and wait for the go-ahead.

	  \item Set $\txns[(\user,\epoch_{\mathsf{cur}})] \leftarrow
\txns[(\user,\epoch_{\mathsf{cur}})] \cup \{\payload\}$.

	  \item Return $\IDsubmitend$ to $\user$ and $\simu$.

	\end{enumerate}

	\fuinterface{\IDgrant} On input $(\IDgrant, \auditor, \epoch)$ from $\user$, send
$(\IDgrant, \user, \epoch)$ to auditor $\auditor$ and wait for confirmation. On
receiving confirmation, do:

	\begin{enumerate}

	  \item If $\reg[\user] = \bot$, then stop.

	  \item If $\epoch \leq \epoch_{\mathsf{cur}}$, then stop.

	  \item Send $(\IDgrant, \auditor, \user, \epoch)$ to $\simu$ and wait
for the go-ahead. On receiving it, do:

	    \begin{enumerate}

	      \item Set $\perm[(\auditor,\user,\epoch)] \leftarrow
\mathsf{true}$.

	      \item Return $\IDgrantend$ to $\user$, $\auditor$, and $\simu$.

	    \end{enumerate}

	\end{enumerate}

	\fuinterface{\IDidentify} On input $(\IDidentify, \user, \epoch)$ from auditor
$\auditor$, do:

	\begin{enumerate}

	  \item If $\perm[(\auditor,\user,\epoch)] \neq \mathsf{true}$, then
stop.

	  \item Otherwise, set $T \leftarrow \txns[(\user,\epoch)]$.

	  \item If $\auditor \in \Cor$, then $T^\star \leftarrow T$, and otherwise
$T^\star \leftarrow \varnothing$.

	  \item Return $(\IDidentifyend, T)$ to $\auditor$ and $(\IDidentifyend,
T^\star)$ to $\simu$.

	\end{enumerate}

	\fuinterface{\IDincepoch} On input $\IDincepoch$ from the ledger operator,
set $\epoch_{\mathsf{cur}} \leftarrow \epoch_{\mathsf{cur}} + 1$.

    \end{framed}
