\section{Construction}\label{sec:txid-construction}

The protocol proceeds as follows. The ledger operator processes user
transactions. Each user is provisioned with a long-term signing key and a
long-term tracing key, cryptographically bound together via a credential issued
by the registration authority. For each epoch, the user derives an epoch tracing
key from their tracing key and the epoch identifier. Transactions submitted
during that epoch are tagged using a pseudorandom function (PRF) $\FT$, evaluated on the epoch tracing key
and an index in the range $[0,\Max)$, where $\Max$ bounds the number of
transactions a user can submit per epoch. Each transaction carries a proof that
its tag was correctly generated.

For tracing, the user discloses their epoch tracing key to the relevant auditor,
who locally computes every valid transaction tag for that user and epoch.

When the system moves to a new epoch, users derive a fresh epoch tracing key,
and tracing capabilities granted for prior epochs expire automatically.

\paragraph{The index is unordered.} The index $\gamma \in [0,\Max)$ replaces
the monotonically increasing counter of prior tag-based
schemes~\cite{CCS:KiaKohSar22,CANS:SarKiaKoh24}. The auditor evaluates $\FT$ at
every index in $[0,\Max)$, so gaps and out-of-order use cost nothing, and users
can create and submit transactions in parallel. The only constraint is that a
user does not reuse an index within an epoch. So $\Max$ is also a per-user,
per-epoch rate limit.

\paragraph{Building blocks.} The protocol is built from five cryptographic
primitives. The registration authority certifies users'
keys with a digital signature scheme $\DS$.  Users bind their tracing keys
across several proofs using a commitment scheme $\Com$. Two pseudorandom
functions, $\FE$ for epoch keys and $\FT$ for tags, derive epoch tracing keys
and transaction tags from users' long-term tracing keys. These keys are also
bound using one-way functions $\G$ and $\G'$,
where $\G'$ is applied to the tracing key as a whole, which the instantiation
takes to be a tuple. The images $\PSK = \G(\sk)$ and $\PTK = \G'(\utk)$ are
users' public signing and tracing keys, and the public tracing key doubles as a
public parameter of $\FT$. Users prove that these values were derived
correctly, and, where a proof must also authenticate a message, that the
message came from the same user, using zero-knowledge proofs of knowledge.

\begin{outline}
  \item why each primitive is needed, in turn
  \item PRF for tags: a tag must look random to anyone without the epoch key (unlinkability of one user's transactions) yet be recomputable by whoever holds it (auditor finds every transaction); a PRF gives exactly both, a one-way or hash function only the first
  \item two PRFs, not one: tags directly under the long-term key would mean granting one epoch hands over every epoch; a fresh epoch key via a second PRF makes epochs independent
  \item commitment: ties the user's several proofs to one hidden tracing key (binding: no key switching between proofs; hiding: the commitment reveals nothing about the key)
  \item one-way functions: public image of each secret key that can be certified and checked
  \item signature: registration authority certifies that image once, later proofs rely on it
  \item proofs: of knowledge (simulator extracts keys) and zero knowledge (published on the ledger)
\end{outline}

\begin{outline}
  \item the broad idea, one or two sentences: the long-term tracing key derives one epoch key per epoch ($\ek_1, \ek_2, \ek_3, \ldots$), and each epoch key derives that epoch's tags; each derivation comes with a proof that it was computed correctly
  \item each step must be one way in the right direction: an epoch key reveals neither the long-term key nor other epochs' keys, and a tag reveals no key; the instantiation section comes back to why this is hard
\end{outline}

$\FT$ also takes the public tracing key $\PTK$ as a public parameter, and we
require both pseudorandom functions to be pseudorandom against a distinguisher
holding $\PTK$.

\begin{outline}
  \item if wanted, one generic sentence on why $\PTK$ is a parameter of $\FT$ and not part of the output of $\FE$: anything a tag needs beyond the epoch key does not change with the epoch, and an output of $\FE$ that repeated every epoch could not be pseudorandom
\end{outline}

\paragraph{Setup.} During setup, the registration authority generates a key pair
for a digital signature scheme. Their public key is communicated to the ledger
operator. The ledger operator generates the public parameters for a commitment
scheme and for four proof systems, used respectively for registration, for epoch
tracing key derivation, for transaction authorisation, and for tag correctness.
The four relations are as follows.

The first relation, $\rel_4$, lets a user prove knowledge of their long-term
signing and tracing keys. Its instance, witness, and relation are as follows:
%
\begin{equation*}
%
  \inst_4 = (\G, \G', \PSK, \PTK), \qquad \witness_4 = (\sk, \utk),
%
\end{equation*}
%
\begin{equation*} \begin{gathered}
%
  \rel_4 = \{\ \PSK = \G(\sk) \ \wedge \ \PTK = \G'(\utk)\ \}.
%
\end{gathered} \end{equation*}
%
The second relation, $\rel_5$, captures correctness of epoch tracing key
generation, with instance, witness, and relation given as follows:
%
\begin{equation*}
%
  \inst_5 = (\FE, \G', \PTK, \epoch, \ek), \qquad \witness_5 = \utk,
%
\end{equation*}
%
\begin{equation*} \begin{gathered}
%
  \rel_5 = \{\ \PTK = \G'(\utk) \ \wedge \ \ek = \FE(\utk, \epoch)\ \}.
%
\end{gathered} \end{equation*}
%
The third relation, $\rel_6$, has two purposes. It lets a user prove
possession of a valid registration credential, and prove that the tracing key
certified by that credential is the one inside a commitment. Its instance,
witness, and relation are as follows:
%
\begin{equation*}
%
  \inst_6 = (\G, \G', \rapk, \ck, \com), \qquad \witness_6 = (\signature, \sk,
\utk, \openinfo),
%
\end{equation*}
%
\begin{equation*} \begin{gathered}
%
  \rel_6 = \{\ \DSverify(\rapk, \G(\sk) \| \G'(\utk), \signature) = 1 \ \wedge \
\com = \ComCommit(\ck, \utk, \openinfo)\ \}.
%
\end{gathered} \end{equation*}
%
The fourth relation, $\rel_7$, lets a user prove that a given epoch tracing key
and transaction tag were correctly derived from the tracing key contained in the
same commitment, with instance, witness, and relation defined as follows:
%
\begin{equation*}
%
  \inst_7 = (\FE, \FT, \G', \ck, \com, \epoch, \Max, \Tag_\gamma), \qquad
\witness_7 = (\utk, \openinfo, \ek, \gamma),
%
\end{equation*}
%
\begin{equation*} \begin{gathered}
%
  \rel_7 = \{\ \com = \ComCommit(\ck, \utk, \openinfo) \ \wedge \ \ek =
\FE(\utk, \epoch) \\ \wedge \ \Tag_\gamma = \FT(\G'(\utk), \ek, \gamma) \ \wedge
\ 0 \leq \gamma < \Max\ \}.
%
\end{gathered} \end{equation*}
%
The ledger operator then publishes the following, where we write
$\ledger[\crs]$ for the public parameters recorded on the ledger, and later
$\ledger[\Tag]$ for the entry recorded under tag $\Tag$:
%
\begin{equation*} \ledger[\crs] \leftarrow (\G, \G', \FE, \FT, \rapk, \ck,
\crs_4, \crs_5, \crs_6, \crs_7, \Max).  \end{equation*}

\begin{outline}
  \item why four relations, to rewrite: validators accept or reject each transaction alone and non-interactively, without contacting the sender, the registration authority or any auditor
  \item $\rel_4$ at registration (keys certified once), $\rel_5$ at a grant (epoch key handed to an auditor), $\rel_6$ and $\rel_7$ on every transaction (registered user, correct tag)
  \item so users, auditors and validators never wait on each other
\end{outline}

\paragraph{Registration.} During registration, users prove knowledge of their
long-term signing and tracing keys, and the registration authority certifies the
corresponding public values, binding them together for future use without ever
learning the keys themselves.

The registration authority first checks that the user has not registered before,
then sends a fresh nonce. The user generates a signing key pair and a tracing
key, derives the corresponding public values $\PSK$ and $\PTK$, and responds with a
zero-knowledge proof of knowledge of both secrets, bound to the nonce so the
proof cannot be replayed, as captured by $\rel_4$.

If the proof verifies, the registration authority certifies the public values
with $\DSsign$, records the user as registered, and returns the resulting
signature. Together with the public values, this signature becomes the user's
registration credential.

\paragraph{Authorisation.} Authorisation for an epoch $\epoch$ happens before it starts. An auditor
requests tracing authorisation from a user, identifying themselves and supplying
a fresh nonce. In response, the user derives their epoch tracing key from their
long-term tracing key and the epoch identifier, and proves that this derivation
is correct, as captured by $\rel_5$.

To authorise this particular auditor, the user binds the epoch key proof and the
auditor's nonce together with a second zero-knowledge proof of knowledge of
their long-term keys, again relative to $\rel_4$, preventing the authorisation
from being replayed elsewhere. The user then sends the auditor their
registration credential, the epoch tracing key, and both proofs. The auditor
accepts the key once the credential verifies with $\DSverify$ and both proofs
check out.

The auditor already knows the user's identity, so the registration credential is
sent in the clear.

\paragraph{Transaction submission.} During transaction submission, the user
proves that the transaction tag was correctly generated from their tracing key,
while also authenticating the transaction itself.

The user prepares a confidential payload and picks a fresh, unused index within
the epoch's allowed range. They derive the transaction tag from their epoch
tracing key and that index, and commit afresh to their long-term tracing key. Both proofs below refer to
this commitment rather than to the key itself.

Two proofs accompany the transaction. The first shows that the tag and the fresh
commitment are consistent with each other and with a single underlying tracing
key, and that the index lies in $[0,\Max)$, as captured by $\rel_7$. The
second binds the whole transaction, the payload, the tag, the commitment, and
the first proof, to a valid registration credential for that same committed key,
as captured by $\rel_6$. Since this proof must authenticate a message rather
than merely certify correctness, it is generated by running $\NIZKprove$ with
the rest of the transaction, the message being signed, as its label. The user submits the
resulting tuple to the ledger.

The transaction validators run $\algo{Verify}$, rejecting the transaction
outright if its tag has already accompanied a previously accepted transaction,
since a repeated tag would let two transactions share an index and become
linkable. Otherwise, they accept the transaction once both proofs verify with
$\NIZKverify$, one against $\rel_7$ and the other against $\rel_6$, and record
the payload against the tag.

The clause $0 \leq \gamma < \Max$ in $\rel_7$ is needed because an auditor
holding $\ek$ evaluates $\FT$ only at indices in $[0,\Max)$. A user who could tag
a transaction with $\gamma = \Max$ would obtain a transaction that no permission
can ever trace. Together with the validators' check that tags are unique, which
stops users reusing an index, the range clause makes $|\txns[(\user,\epoch)]|
\leq \Max$ hold in the real world, as step 3 of $\IDsubmit$ in
$\idfu{\algo{trace}}$ requires. So the validators enforce both checks on
every transaction.

\paragraph{Tracing.} To trace a user in epoch $\epoch$, the auditor uses the user's public tracing
key $\PTK$ and epoch key $\ek$. It traces the transactions the user submitted
during that epoch by computing $\Tag_\gamma = \FT(\PTK, \ek, \gamma)$ for each
index $\gamma \in [0,\Max)$ and retrieving entry $\ledger[\Tag_\gamma]$ where
present. Both values reach the auditor in the grant message of the epoch, so
tracing requires no state carried over from any earlier epoch.

\paragraph{Increment Epoch.} When an epoch
ends, all participants move to epoch $\epoch + 1$, and every grant for the old
epoch lapses.

The complete protocol is given in \Cref{prot:txid-generic}. It is stated
generically in the signature scheme, the commitment scheme, the one-way
functions, the two pseudorandom functions and the four proof systems, and
\Cref{sec:txid-instantiation} instantiates each of them. The instances and
witnesses $\inst_i$ and $\witness_i$ are those of $\rel_4$ to $\rel_7$ above,
and we write $\state$ for the ledger, a table of payloads indexed by tag.

\begin{protocolbox}{Transaction tracing}{txid-generic}

  \begin{description}

    \item[$(\crs,\state) \sample \IDgen(\secparam)$ :] On input the security
parameter, do:

      \begin{enumerate}

	\item The registration authority samples $(\rask,\rapk) \sample
\DSgen(\secparam)$ and sends $\rapk$ to the ledger operator.

	\item The ledger operator samples $\ck \sample \ComGen(\secparam)$ and
$\crs_i \sample \NIZKgen(\secparam,\rel_i)$ for each $i \in \{4,5,6,7\}$, and
fixes $\G$, $\G'$, $\FE$, $\FT$ and $\Max$.

	\item Return $\crs \leftarrow
(\G,\G',\FE,\FT,\rapk,\ck,\crs_4,\crs_5,\crs_6,\crs_7,\Max)$ and $\state
\leftarrow \varnothing$.

      \end{enumerate}

    \item[$(\sk,\utk,\regcred) \sample \IDregister(\crs,\state)$ :] Between the
user and the registration authority, do:

      \begin{enumerate}

	\item The registration authority sends a fresh nonce $\rand$ to the
user.

	\item The user samples $\sk$ and $\utk$, and computes $\PSK \leftarrow
\G(\sk)$, $\PTK \leftarrow \G'(\utk)$ and $\algoproof_4 \sample
\NIZKprove(\crs_4,\inst_4,\witness_4,\rand)$.

	\item The user sends $(\PSK,\PTK,\algoproof_4)$ to the registration
authority.

	\item The registration authority exits if $\PSK$ has been registered
before or $\NIZKverify(\crs_4,\inst_4,\algoproof_4,\rand) = 0$.

	\item The registration authority computes $\signature \sample
\DSsign(\rask,\PSK\|\PTK)$ and records $\PSK$ as registered.

	\item Return $\sk$ and $\utk$ to the user, and $\regcred \leftarrow
(\PSK,\PTK,\signature)$ as their registration credential.

      \end{enumerate}

    \item[$(\PTK,\ek) \sample \IDgrant(\crs,\sk,\utk,\regcred,\epoch)$ :]
Between the user and an auditor, do:

      \begin{enumerate}

	\item The auditor sends a fresh nonce $\rand$ to the user.

	\item The user parses $\regcred = (\PSK,\PTK,\signature)$, and computes
$\ek \leftarrow \FE(\utk,\epoch)$ and $\algoproof_5 \sample
\NIZKprove(\crs_5,\inst_5,\witness_5,\rand)$.

	\item The user computes $\algoproof_4 \sample
\NIZKprove(\crs_4,\inst_4,\witness_4,\algoproof_5\|\rand)$ and sends
$(\regcred,\ek,\algoproof_5,\algoproof_4)$ to the auditor.

	\item The auditor outputs $(\PTK,\ek)$ if the following all hold, and
exits otherwise:
	  %
	  \begin{gather*}
	    \DSverify(\rapk,\PSK\|\PTK,\signature) = 1, \quad
	    \NIZKverify(\crs_5,\inst_5,\algoproof_5,\rand) = 1, \\
	    \NIZKverify(\crs_4,\inst_4,\algoproof_4,\algoproof_5\|\rand) = 1.
	  \end{gather*}

      \end{enumerate}

    \item[$\tx \sample \IDsubmit(\crs,\sk,\utk,\regcred,\epoch,\payload)$ :] On
input from the user, do:

      \begin{enumerate}

	\item Parse $\regcred = (\PSK,\PTK,\signature)$ and compute $\ek
\leftarrow \FE(\utk,\epoch)$.

	\item Take a fresh, unused index $\gamma \in [0,\Max)$ from the user's
local pool for this epoch, and compute $\Tag_\gamma \leftarrow
\FT(\PTK,\ek,\gamma)$.

	\item Sample $\openinfo$ and compute $\com \leftarrow
\ComCommit(\ck,\utk,\openinfo)$.

	\item Compute $\algoproof_7 \sample
\NIZKprove(\crs_7,\inst_7,\witness_7)$.

	\item Set $\msg \leftarrow \payload\|\Tag_\gamma\|\com\|\algoproof_7$
and compute $\algoproof_6 \sample \NIZKprove(\crs_6,\inst_6,\witness_6,\msg)$.

	\item Return $\tx \leftarrow
(\payload,\Tag_\gamma,\com,\algoproof_7,\algoproof_6)$, and submit it to the
ledger.

      \end{enumerate}

    \item[$\{0,1\} \leftarrow \algo{Verify}(\crs,\state,\tx)$ :] Run by the
transaction validators. Parse $\tx =
(\payload,\Tag_\gamma,\com,\algoproof_7,\algoproof_6)$, set $\msg \leftarrow
\payload\|\Tag_\gamma\|\com\|\algoproof_7$, and return $1$ if and only if the
following hold:
      %
      \begin{gather*}
	\Tag_\gamma \notin \state, \\
	\NIZKverify(\crs_7,\inst_7,\algoproof_7) = 1, \quad
	\NIZKverify(\crs_6,\inst_6,\algoproof_6,\msg) = 1.
      \end{gather*}
      %
      On returning $1$, the validators set $\state[\Tag_\gamma] \leftarrow
\payload$.

    \item[$\{\payload\} \leftarrow \IDidentify(\crs,\PTK,\ek,\epoch)$ :] For
each $\gamma \in [0,\Max)$, compute $\Tag_\gamma \leftarrow
\FT(\PTK,\ek,\gamma)$ and retrieve $\state[\Tag_\gamma]$ if present. Return
the set of retrieved payloads.

  \end{description}

\end{protocolbox}

\begin{theorem}\label{thm:txid-bb} Assuming that $\DS$ satisfies existential
unforgeability, $\FE$ and $\FT$ are pseudorandom against a distinguisher holding
$\PTK$, $\G$ and $\G'$ are one way, and the zero-knowledge proof systems for
$\rel_4$ through $\rel_7$
are zero knowledge and simulation extractable, the protocol described above
securely realises $\idfu{\algo{trace}}$.  \end{theorem}
