\section{Construction}\label{sec:txid-construction}

The ledger operator processes users'
transactions. Each user is provisioned with a long-term signing key and a
long-term tracing key, cryptographically bound together through a credential issued
by the registration authority. For each epoch, the user derives an epoch tracing
key from their tracing key and the epoch identifier. Transactions submitted
during that epoch are tagged using a pseudorandom function (PRF) $\FT$, evaluated on the epoch tracing key
and an index in the range $[0,\Max)$, where $\Max$ bounds the number of
transactions a user can submit per epoch. Each transaction carries a proof that
its tag was correctly generated.

For tracing, the user discloses their epoch tracing key to the relevant auditor,
who locally computes every valid transaction tag for that user and epoch.

When the system moves to a new epoch, users derive a fresh epoch tracing key,
so a permission granted for one epoch gives nothing in the next.

\paragraph{Building blocks.} The protocol is built from five cryptographic
primitives. The registration authority certifies users'
keys with a digital signature scheme $\DS$.  Users bind their tracing keys
across several proofs using a commitment scheme $\Com$. Two pseudorandom
functions, $\FE$ for epoch keys and $\FT$ for tags, derive epoch tracing keys
and transaction tags from users' long-term tracing keys. These keys are also
bound using one-way functions $\G$ and $\G'$. The images $\PSK = \G(\sk)$ and $\PTK = \G'(\utk)$ are
users' public signing and tracing keys, and the public tracing key doubles as a
public parameter of $\FT$. Users prove with zero-knowledge proofs of knowledge
that these values were derived correctly and, where a proof must also
authenticate a message, that the message came from the same user.

Tags come from a pseudorandom function. A tag must look random to anyone
without the epoch key, so that one user's transactions cannot be linked, and
must be recomputable by whoever holds the key, so that the auditor finds every
transaction. A pseudorandom function gives both, and a one-way or hash function
only the first. There are two pseudorandom functions and not one. Tags computed
directly under the long-term key would mean that a grant for one epoch hands
over every epoch, so a second pseudorandom function derives a fresh key for each
epoch, and epochs are independent. The commitment ties a user's several proofs
to one hidden tracing key. Binding stops users switching keys between proofs,
and hiding means the commitment reveals nothing about the key. The one-way
functions give a public image of each secret key that can be certified and
checked. The registration authority certifies these images once with the
signature scheme, and later proofs rely on that signature. The proofs are proofs of knowledge so that the simulator can extract users'
keys. They are zero knowledge since they are published on the ledger.

The tracing key derives one epoch key per epoch, and each epoch key derives the
tags of its epoch. Each derivation comes with a proof that it was computed
correctly. Each step must be one way in the right direction. An epoch key
reveals neither the tracing key nor the keys of other epochs, and a tag reveals
no key. \Cref{sec:txid-instantiation} comes back to why this is hard to achieve
with short proofs.

$\FT$ also takes the public tracing key $\PTK$ as a public parameter, and we
require both pseudorandom functions to be pseudorandom against a distinguisher
holding $\PTK$. Anything a tag needs beyond the epoch key does not change with
the epoch, so it belongs in $\PTK$, since an output of $\FE$ that repeated in
every epoch could not be pseudorandom.

\paragraph{Setup.} During setup, the registration authority generates a key pair
for a digital signature scheme. The ledger operator generates the public parameters for a commitment
scheme and for four proof systems, used respectively for registration, for epoch
tracing key derivation, for transaction authorisation, and for tag correctness.
The four relations are as follows.

The first relation, $\rel_4$, lets a user prove knowledge of their long-term
signing and tracing keys. Its instance, witness, and relation are as follows:
%
\begin{gather*}
%
  \inst_4 = (\G, \G', \PSK, \PTK), \qquad \witness_4 = (\sk, \utk), \\
  \rel_4 = \{\ \PSK = \G(\sk) \ \wedge \ \PTK = \G'(\utk)\ \}.
%
\end{gather*}
%
The second relation, $\rel_5$, captures correctness of epoch tracing key
generation, with instance, witness, and relation given as follows:
%
\begin{gather*}
%
  \inst_5 = (\FE, \G', \PTK, \epoch, \ek), \qquad \witness_5 = \utk, \\
  \rel_5 = \{\ \PTK = \G'(\utk) \ \wedge \ \ek = \FE(\utk, \epoch)\ \}.
%
\end{gather*}
%
The third relation, $\rel_6$, has two purposes. It lets a user prove
possession of a valid registration credential, and prove that the tracing key
certified by that credential is the one inside a commitment. Its instance,
witness, and relation are as follows:
%
\begin{gather*}
%
  \inst_6 = (\G, \G', \rapk, \ck, \com), \qquad \witness_6 = (\signature, \sk,
\utk, \openinfo), \\
  \rel_6 = \{\ \DSverify(\rapk, \G(\sk) \| \G'(\utk), \signature) = 1 \ \wedge \
\com = \ComCommit(\ck, \utk, \openinfo)\ \}.
%
\end{gather*}
%
The fourth relation, $\rel_7$, lets a user prove that a given epoch tracing key
and transaction tag were correctly derived from the tracing key contained in the
same commitment, with instance, witness, and relation defined as follows:
%
\begin{gather*}
%
  \inst_7 = (\FE, \FT, \G', \ck, \com, \epoch, \Max, \Tag_\gamma), \qquad
\witness_7 = (\utk, \openinfo, \ek, \gamma), \\
  \begin{gathered}
  \rel_7 = \{\ \com = \ComCommit(\ck, \utk, \openinfo) \ \wedge \ \ek =
\FE(\utk, \epoch) \\ \wedge \ \Tag_\gamma = \FT(\G'(\utk), \ek, \gamma) \ \wedge
\ 0 \leq \gamma < \Max\ \}.
  \end{gathered}
%
\end{gather*}

There are four relations because the validators accept or reject each
transaction on their own and non-interactively, without contacting the sender,
the registration authority or any auditor. Users prove $\rel_4$ at
registration, so that their keys are certified once, and $\rel_5$ at a grant,
when an epoch key is handed to an auditor. Every transaction carries proofs for
$\rel_6$ and $\rel_7$, which show that it comes from a registered user and that
its tag is correct. So users, auditors and validators never wait on each other.

\paragraph{Registration.} At registration, users prove knowledge of their
long-term signing and tracing keys, and the registration authority certifies the
corresponding public values, binding them together for future use without ever
learning the keys themselves. The proof is bound to a fresh nonce from the
registration authority, so it cannot be replayed.

\paragraph{Authorisation.} Authorisation for an epoch $\epoch$ happens before it starts. An auditor
requests tracing authorisation from a user, identifying themselves and supplying
a fresh nonce. In response, the user derives their epoch tracing key from their
long-term tracing key and the epoch identifier, and proves that this derivation
is correct, as captured by $\rel_5$.

To authorise this particular auditor, the user binds the epoch key proof and the
auditor's nonce together with a second zero-knowledge proof of knowledge of
their long-term keys, again relative to $\rel_4$, preventing the authorisation
from being replayed elsewhere. The auditor already knows the user's identity, so the registration credential is
sent in the clear.

\paragraph{Transaction submission.} The user commits afresh to their long-term
tracing key, and both proofs below refer to this commitment and not to the key
itself. Two proofs accompany the transaction. The first shows that the tag and the fresh
commitment are consistent with each other and with a single underlying tracing
key, and that the index lies in $[0,\Max)$, as captured by $\rel_7$. The
second binds the payload, the tag, the commitment and the first proof to a valid
registration credential for that same committed key, as captured by $\rel_6$.
This proof must also authenticate a message, so it is generated by running
$\NIZKprove$ with the rest of the transaction as its label.

The transaction validators run $\algo{Verify}$, rejecting the transaction
outright if its tag has already accompanied a previously accepted transaction,
since a repeated tag would let two transactions share an index and become
linkable.

The clause $0 \leq \gamma < \Max$ in $\rel_7$ is needed because an auditor
holding $\ek$ evaluates $\FT$ only at indices in $[0,\Max)$. A user who could tag
a transaction with $\gamma = \Max$ would obtain a transaction that no permission
can ever trace. The validators' check that tags are unique stops users reusing an index.
Together with this check, the range clause makes the bound of $\Max$
transactions per user and epoch hold in the real world, as step 3 of $\IDsubmit$
in $\idfu{\algo{trace}}$ requires.

\Cref{prot:txid-generic} gives the complete protocol. We state it
generically in the signature scheme, the commitment scheme, the one-way
functions, the two pseudorandom functions and the four proof systems, and
\Cref{sec:txid-instantiation} instantiates each of them. The instances and
witnesses $\inst_i$ and $\witness_i$ are those of $\rel_4$ to $\rel_7$ above,
and we write $\state$ for the ledger, a table of payloads indexed by tag.

\begin{protocolbox}{Transaction tracing}{txid-generic}

  \begin{description}

    \item[$(\crs,\state) \sample \IDgen(\secparam)$ :] On input the security
parameter, do:

      \begin{enumerate}

	\item The registration authority samples $(\rask,\rapk) \sample
\DSgen(\secparam)$ and sends $\rapk$ to the ledger operator.

	\item The ledger operator samples $\ck \sample \ComGen(\secparam)$ and
$\crs_i \sample \NIZKgen(\secparam,\rel_i)$ for each $i \in \{4,5,6,7\}$, and
fixes $\G$, $\G'$, $\FE$, $\FT$ and $\Max$.

	\item Return $\crs \leftarrow
(\G,\G',\FE,\FT,\rapk,\ck,\crs_4,\crs_5,\crs_6,\crs_7,\Max)$ and $\state
\leftarrow \varnothing$.

      \end{enumerate}

    \item[$(\sk,\utk,\regcred) \sample \IDregister(\crs,\state)$ :] Between the
user and the registration authority, do:

      \begin{enumerate}

	\item The registration authority sends a fresh nonce $\rand$ to the
user.

	\item The user samples $\sk$ and $\utk$, and computes $\PSK \leftarrow
\G(\sk)$, $\PTK \leftarrow \G'(\utk)$ and $\algoproof_4 \sample
\NIZKprove(\crs_4,\inst_4,\witness_4,\rand)$.

	\item The user sends $(\PSK,\PTK,\algoproof_4)$ to the registration
authority.

	\item The registration authority exits if $\PSK$ has been registered
before or $\NIZKverify(\crs_4,\inst_4,\algoproof_4,\rand) = 0$.

	\item The registration authority computes $\signature \sample
\DSsign(\rask,\PSK\|\PTK)$ and records $\PSK$ as registered.

	\item Return $\sk$ and $\utk$ to the user, and $\regcred \leftarrow
(\PSK,\PTK,\signature)$ as their registration credential.

      \end{enumerate}

    \item[$(\PTK,\ek) \sample \IDgrant(\crs,\sk,\utk,\regcred,\epoch)$ :]
Between the user and an auditor, do:

      \begin{enumerate}

	\item The auditor sends a fresh nonce $\rand$ to the user.

	\item The user exits if the epoch $\epoch$ has started.

	\item The user parses $\regcred = (\PSK,\PTK,\signature)$, and computes
$\ek \leftarrow \FE(\utk,\epoch)$ and $\algoproof_5 \sample
\NIZKprove(\crs_5,\inst_5,\witness_5,\rand)$.

	\item The user computes $\algoproof_4 \sample
\NIZKprove(\crs_4,\inst_4,\witness_4,\algoproof_5\|\rand)$ and sends
$(\regcred,\ek,\algoproof_5,\algoproof_4)$ to the auditor.

	\item The auditor outputs $(\PTK,\ek)$ if the epoch $\epoch$ has not
started and the following all hold, and exits otherwise:
	  %
	  \begin{gather*}
	    \DSverify(\rapk,\PSK\|\PTK,\signature) = 1, \quad
	    \NIZKverify(\crs_5,\inst_5,\algoproof_5,\rand) = 1, \\
	    \NIZKverify(\crs_4,\inst_4,\algoproof_4,\algoproof_5\|\rand) = 1.
	  \end{gather*}

      \end{enumerate}

    \item[$\tx \sample \IDsubmit(\crs,\sk,\utk,\regcred,\epoch,\payload)$ :] On
input from the user, do:

      \begin{enumerate}

	\item Parse $\regcred = (\PSK,\PTK,\signature)$ and compute $\ek
\leftarrow \FE(\utk,\epoch)$.

	\item Take an index $\gamma \in [0,\Max)$ that the user has not used in
this epoch, and compute $\Tag_\gamma \leftarrow
\FT(\PTK,\ek,\gamma)$.

	\item Sample $\openinfo$ and compute $\com \leftarrow
\ComCommit(\ck,\utk,\openinfo)$.

	\item Compute $\algoproof_7 \sample
\NIZKprove(\crs_7,\inst_7,\witness_7)$.

	\item Set $\msg \leftarrow \payload\|\Tag_\gamma\|\com\|\algoproof_7$
and compute $\algoproof_6 \sample \NIZKprove(\crs_6,\inst_6,\witness_6,\msg)$.

	\item Return $\tx \leftarrow
(\payload,\Tag_\gamma,\com,\algoproof_7,\algoproof_6)$, and submit it to the
ledger.

      \end{enumerate}

    \item[$\{0,1\} \leftarrow \algo{Verify}(\crs,\state,\tx)$ :] Run by the
transaction validators. Parse $\tx =
(\payload,\Tag_\gamma,\com,\algoproof_7,\algoproof_6)$, set $\msg \leftarrow
\payload\|\Tag_\gamma\|\com\|\algoproof_7$, and return $1$ if and only if the
following hold:
      %
      \begin{gather*}
	\Tag_\gamma \notin \state, \\
	\NIZKverify(\crs_7,\inst_7,\algoproof_7) = 1, \quad
	\NIZKverify(\crs_6,\inst_6,\algoproof_6,\msg) = 1.
      \end{gather*}
      %
      On returning $1$, the validators set $\state[\Tag_\gamma] \leftarrow
\payload$.

    \item[$\{\payload\} \leftarrow \IDidentify(\crs,\PTK,\ek,\epoch)$ :] For
each $\gamma \in [0,\Max)$, compute $\Tag_\gamma \leftarrow
\FT(\PTK,\ek,\gamma)$ and retrieve $\state[\Tag_\gamma]$ if present. Return
the set of retrieved payloads.

  \end{description}

\end{protocolbox}

\begin{theorem}\label{thm:txid-bb} Assuming that $\DS$ satisfies existential
unforgeability, $\Com$ is binding and hiding, $\FE$ and $\FT$ are pseudorandom
against a distinguisher holding $\PTK$, $\G$ is one way, and the
proof systems for $\rel_4$ through $\rel_7$ are zero knowledge and simulation
extractable, the protocol described above securely realises
$\idfu{\algo{trace}}$ in the standalone model against static corruption, with
secure channels between honest users and auditors.  \end{theorem}

\paragraph{Extensions.} Dropping the check that the epoch has not started gives
retrospective grants. Tags depend only on the epoch key and the index, so an
auditor given the epoch key of a past epoch traces it as before. The proof of
\Cref{thm:txid-bb} does not cover this. Until a grant arrives, the simulator
publishes uniform tags, and a later grant would need an epoch key under which
these tags are correct. A pseudorandom function that the simulator can program
after the fact, such as one modelled as a random oracle, would allow this. We
leave retrospective grants to future work.
